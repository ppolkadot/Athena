# Athena 1.1.0 workflow and design revision brief

**Status:** Product decisions D1, D2, and D3 confirmed; task-level plan integration remains required.
**Prerequisite:** Athena 1.0.2 with its finalized typography, overflow, and contrast foundation; do not base this work on an obsolete 1.0.0 visual contract.
**Original plan:** [2026-11-11-athena-1.1.0.md](../plans/2026-11-11-athena-1.1.0.md)
**Decision register:** [Roadmap revision](2026-11-13-athena-roadmap-revision.md)
**Readiness supplement:** [2026-11-16 review](2026-11-16-athena-readiness-and-appearance-review.md), including confirmed cross-screen wallpaper scope and the Rust-only constraint. Existing detailed examples remain unready until reconciled; this brief is not a substitute for that work.

## Goal and retained scope

Deliver reliable settlement, one-line entry, trash/undo, backup/restore, JSON import, day drill-down, monthly insight, templates, duplicate warnings, and XLSX. Introduce the shared Apple/Onyx visual and motion system in this version, following confirmed D1.

Keep exact integer cents, offline operation, `Store::apply` as the mutation boundary, cached view models, localized copy, and schema migration 0002. No accounts, bank integration, or automatic financial transfers.

## Correctness work to incorporate

### Recoverable backup replacement

**Owning files:** `src/infrastructure/db/backup.rs`, `src/infrastructure/db/mod.rs`, `src/app/store.rs`, `src/lib.rs`, and Settings.

- Validate candidate integrity, required Athena schema, supported version, and domain invariants before closing the current database. An integrity-valid unrelated SQLite file or unsupported schema must not replace it.
- Produce a verified pre-restore snapshot and a standalone candidate in the data directory. Keep the instance lock for the entire operation.
- Specify durable recovery states for: prepared candidate, original renamed, candidate installed, candidate reopened, and cleanup complete. Persist sufficient operation state to distinguish these after a crash.
- Recovery must handle both `athena.db` and `.old` existing. On rollback, close candidate handles and handle its journal files before returning the original to its live path; do not rename onto an occupied destination on Windows.
- Keep the original until the replacement connection and Store/view-model reload are usable. Preserve an accessible recovery route if reopening either database fails.
- Retention acts only on recognized backup files. Protect the snapshot required by an unfinished restore/import regardless of normal pruning.

**Acceptance:** file-backed WAL tests inject failure at each filesystem/reopen boundary, restart from every persisted recovery state, and verify original rows and allocations remain usable. Include unsupported schema, unrelated database, locked file, name collision, and interrupted restore.

### Balanced settlement with visible coverage

**Owning files:** settlement service/repository queries, `ViewModel`, Month, and i18n.

- D2 selects complete-entry balances with visibly labeled exclusions and a repair filter.
- Include an expense/refund only when its payer is known and its nonempty allocations satisfy the amount invariant. Exclude it from both paid and owed otherwise.
- Display the excluded count and a repair filter. Distinguish unknown payer from unassigned responsibility. Income is excluded entirely.
- Calculate the participant set from relevant historical people, including archived participants. Do not choose a two-person sentence merely because only two people are currently active.

**Acceptance:** balanced subset sums to zero; expense/refund direction is correct; unknown payer, missing allocations, zero-cent shares, and archived participants cannot create an unsupported creditor or payment instruction.

### Versioned and validated import/export

**Owning files:** export DTOs, `src/infrastructure/export/json.rs`, import service/repository, transaction domain validation, and integrity checks.

- Introduce document format 2 for the new 1.1 import/export contract. Accept format 1 through an explicit compatibility adapter; reject unknown future versions before any replacement. Document format versions are independent of database migration versions.
- Do not rely on permissive unknown-field deserialization to accept future persisted collections.
- Define exported record metadata so new documents preserve transaction/profile timestamps. For genuine format-1 documents, use a documented deterministic fallback from a validated export timestamp; never claim that fallback is the original creation time.
- Reuse domain invariants for splits and references, allowing existing zero-allocation and zero-cent-share cases where valid. Historical archived references must remain importable; interactive active-picker rules must not discard history.
- Validate IDs, duplicate per-person allocations, supported currency, dates/months, timestamps, positive amounts, checked sums, and required collections. Validate before writing and recheck inside the transaction.
- Seed an existing target for replacement-failure tests. Compare the complete canonical payload on round-trip, normalizing only documented version/provenance fields and compatibility defaults.
- Correct `export_json` examples to pass the explicit timestamp argument. Test nonempty templates, profile settings, IDs, and record timestamps.

**Acceptance:** future-format rejection and every late validation/write failure leave the existing profile, people, categories, templates, and transactions intact; a pre-import recovery snapshot exists before replacement.

### Fast entry, templates, insight, and day navigation

- One-line entry owns its first Enter, including failed parsing. It fills a reviewable draft and never reaches the general save handler in that frame. A deliberate subsequent save creates exactly one transaction. Define its reset/focus behavior for repeated entry and exclude edit mode.
- A negative parsed amount must lead to an explicit correction or transaction-type choice; never silently convert it into an expense/refund. Dates, payer, and responsibility stay visible before saving.
- D3 selects full fidelity. Extend migration 0002 and the export DTO with payer, an explicit responsibility mode, and per-person allocation instructions. Preserve the supported form fields, including kind, category, description, and shared/custom splits. A template applies today's date as the existing quick-entry contract specifies; the UI must make that date visible rather than silently reusing an old transaction date.
- Amount edits must recompute or require repair according to the existing even/custom split rules; a copied split must never silently stop summing to the new amount. Archived references require explicit reassignment before a new transaction is saved. Applying a template fills the form only and handles replacement of an already edited draft deliberately.
- Duplicate confirmation works with keyboard and mouse, resets on any meaningful draft change, excludes the edited row and trash, and never auto-deletes.
- Define income-only, refund-only, zero-spending, and negative-spending insight wording. Resolve category labels by current IDs instead of adding an undefined `CategoryTotal.name` field to a fixture.
- Cache day totals and activity counts in `ViewModel`. Spending heat and activity markers are separate, so salary-only or net-zero dates remain discoverable. Day selection is keyboard accessible, localized, and cleared when changing months.

## Apple/Onyx design system proposal

Following D1, establish shared tokens and components before styling each new feature independently. The product direction is confirmed; detailed visual compositions and material effects still require visual validation against these constraints.

- Register-first composition: a compact balance/summary header, a stable transaction column, and a secondary rail that stacks below content when width or text scaling requires it.
- Onyx dark theme: near-black canvas, charcoal navigation, slightly raised panels, restrained highlights, and the existing blue identity. Keep the light theme equally complete.
- Use opaque financial reading surfaces. Reserve a subtle material treatment for navigation and temporary overlays; true backdrop blur needs a measured feasibility check and an opaque fallback.
- Preserve Semibold main text, real Bold titles, and Semibold tabular money/dates. Use size, spacing, and semantic color to keep hierarchy clear despite the heavier base weight.
- Embed a consistent icon set rather than relying on host-only symbol coverage in the final visual system. Keep accessible names and visible focus.
- Add design tokens for spacing, density, corner radius, text roles, elevation, and states. Capture the approved result in product/design documentation rather than treating screenshots as the sole contract.

### Proposed motion contract

- Hover/press color feedback: 90–120 ms; selection: 140–180 ms.
- Month navigation: 180–220 ms, restrained directional movement and crossfade, interruptible on repeated navigation.
- Modal entrance: 180–220 ms; dismissal: 120–150 ms. Input and Escape remain responsive during transitions.
- Row insertion/removal: 120–180 ms, preserving focus and scroll position. Do not animate monetary values through misleading intermediate amounts.
- Add reduced-motion behavior and a persisted user override in migration 0002 if the final design includes a setting. Honor the Windows motion preference when available; define the fallback explicitly.
- Stop nonessential loops when hidden and stop repaint requests when settled. Remove spatial movement under reduced motion while retaining clear state feedback.
- Snapshot tests capture stable final states; additional deterministic interaction tests cover interruption and reduced motion.

These values are starting targets for the implementation plan, not an approved visual comp or a claim of measured performance.

## Interaction and accessibility additions

- Undo is an accessible action. Its timeout pauses while hovered/focused, and Trash remains a durable recovery path after the toast expires. Start its lifetime on first display, following the current pending-toast behavior.
- Define deletion confirmation policy consistently with undo; irreversible purge always explains the consequence. Disclose automatic trash retention and avoid silently treating a clock jump as user intent to purge.
- Return keyboard focus to the initiating control after dialogs. Preserve selected rows or choose the nearest remaining row after removal. Define what happens to unsaved drafts on navigation.
- Import/restore previews show source, target, counts, replacement consequence, and recovery location. Keep the recovery location accessible in Settings rather than only in an expiring toast.
- Keep `Ctrl+1/2/3` mapped to Month/Calendar/Settings and `Ctrl+4` to Trash, even if sidebar order differs. Expose shortcuts accessibly. Add a focused-search shortcut without intercepting text editing.
- Keep expensive data operations from presenting as frozen controls: show an operation state, prevent duplicate submission, preserve the instance lock, and define when cancellation is still safe.

## Appearance and customization expansion (review 2026-11-16)

- The user requests GIF wallpaper across all main screens and additional customization. Keep the shell-level background shared across navigation, including later Goals; do not restart playback per screen. Solid financial surfaces and a contrast scrim retain reading clarity.
- Retain Rust/egui. Prototype wallpaper-sampling glass with a version-matched wgpu callback and WGSL, using the supplied shader as an algorithm reference. Keep text and inputs outside refraction. Visual parity and performance remain unverified until the experiment passes.
- Proposed controls: curated dark/light presets and accents, density and app text scale, local static/GIF wallpaper, fit/dimming, pause, motion/transparency overrides, quality, and Reset Appearance. Preview/Apply/Cancel preserves open drafts and the previous applied appearance on failure.
- Bound local decoding and retained frame memory, cancel stale worker results, release replaced textures, and stop decorative loops when hidden/paused/reduced-motion. Do not load the reference's remote video or introduce network behavior.
- Define managed-asset storage, portable behavior, missing-file fallback, and truthful JSON/database-backup coverage before writing migration 0002 or format 2. The review recommends optional managed media outside SQLite and explicitly discloses its exclusion from database-only backups.
- Add keyboard help, visible filter scope, retained drafts, and persistent recovery status as core quality requirements. Session amount masking is a useful optional feature, distinct from encryption or access control.
- The supplement supplies concrete ownership, proposed resource limits, test cases, and rollout gates. These controls and budgets are planning recommendations, not a finished visual approval or implemented functionality.

## Incorporation sequence and release acceptance

1. Rebase the original plan on the finalized 1.0.2 contract and the confirmed D1–D3 choices.
2. Specify migration 0002, compatibility DTOs, and recovery states together.
3. Implement and verify restore/import/trash invariants before adding their user-facing triggers.
4. Add settlement and fast-entry workflows with their keyboard regression tests.
5. Apply the approved shared design/motion system; then complete day drill-down, insights, templates, duplicate warnings, and XLSX.
6. Verify XLSX sheet contents, types, scope, and currency values, not just ZIP magic/nonempty bytes. Document the existing cents-to-spreadsheet-float boundary and test its supported precision.
7. Update Cargo, lockfile, installer, README, design documentation, localized copy, snapshots, and `docs/smoke-1.1.md` together.

Release gates include formatting, Clippy, the full tests, release build, document lint, v1-to-v2 database upgrade, failed-operation recovery, native keyboard/screen-reader checks, both themes/languages, Windows scaling, reduced motion, and installed-license verification. Test results belong to the actual final executable/installer hashes.
