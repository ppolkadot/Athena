## Goal and boundaries

Add savings goals and trustworthy snapshots for completed months. Contributions track progress only; they do not create transactions or alter tracked balance. A closing is a saved comparison snapshot, not a lock preventing later transaction edits.

Keep structured, language-independent data; resolve intentional live labels through current people/categories; retain fallbacks where deletion can remove a label source. Use the approved 1.1–1.3 components and motion rules rather than introducing a second visual style.

## Goal domain and lifecycle

**Owning files (revised to 1.4.0):** migrations `0006_goals` / `0007_closings` (superseding the obsolete `0003` reference), goal domain/service/repository, `AppAction`, `ViewModel`, `GoalsState`, Goals screen, and i18n.

- Compute contributed cents with checked accumulation. Reject an addition/import that exceeds the representable total inside the same transaction; widening the percentage multiplication alone is insufficient.
- Preserve exact contributed money, clamp displayed remaining to zero, and cap the progress indicator at 100%. Show any excess explicitly rather than losing it through the cap.
- Validate target amount, calendar dates, per-person references, and every contribution before writing. Preserve historical archived-person attribution while restricting choices for new assignments.
- D4 keeps `Funded` derived from contribution progress and `Completed` as a deliberate workflow status. A funded active goal may be completed by the user; a completed goal is read-only until reopened. Manual completion below target is allowed and continues to show the actual percentage and remaining amount honestly.
- Paused goals retain history, suppress scheduled-contribution prompts, and can receive deliberate contributions. Archiving hides a goal without deleting it; provide an Archived filter and Restore action. Preserve the pre-archive workflow state so Restore returns to that state, using an explicit stored field in migration 0003 rather than guessing from the current funded percentage.
- Deleting a contribution always confirms, recomputes progress, and updates the detail/list views. It must not silently rewrite a manual workflow status.
- Removing contributions or increasing a target recomputes `Funded`; it does not change the manual workflow status. Changing a completed goal requires an explicit Reopen action first. Archive and Restore never synthesize a completion decision.

**Acceptance:** boundary-value accumulation, overfunding, manual completion below target, removal after funding, target edits, pause/resume, archive/restore of each workflow state, and archived-person history each have explicit tests.

## Contribution plan and read models

- Inject the local date into contribution-plan calculations. Specify same-day, past-deadline, end-of-month, leap-year, and weekly-rounding behavior in examples before implementing arithmetic.
- Zero periods produce a clear overdue/due-today message with the full remaining amount; never display an instruction to contribute per zero periods.
- Do not show a saving schedule for paused, completed, or archived goals. No-target goals show progress without an invented deadline.
- Add a selected-goal detail read model containing contribution IDs, dates, amounts, and notes. Progress aggregates alone cannot populate the list or identify a row to delete.
- Invalidate that read model on selection, contribution writes, import/restore, and goal edits. Refresh time-sensitive hints at local midnight and after resume from sleep, even if `data_version` did not change.
- Update cached attribution and closing labels on the existing partial People/Categories refresh paths. Screens still never query the database from `show`.

**Acceptance:** opening an existing goal immediately shows its contribution history; add/delete updates both detail and summary; midnight and rename tests prove caches cannot retain stale text or schedules.

## Complete monthly-closing snapshot

**Owning files (revised to 1.4.0):** migrations `0006_goals` / `0007_closings` (superseding obsolete `0003`), closing domain/repository/service, reports/insight services, `ViewModel`, Month, Calendar, and exports.

- Store current income, expenses, refunds, result, count, and the existing largest-expense ID/title/amount snapshot.
- Add `previous_spending` and `previous_count`, retaining previous result only if a displayed comparison uses it. Net result cannot substitute for spending when reproducing a spending-comparison sentence.
- Store the winning category's amount as `top_category_net: Option<Money>` alongside `top_category_id: Option<i64>`. A positive amount with a null ID represents an uncategorized winner; no amount represents no winner. Its name is localized at display time.
- Persist sufficient inputs to generate the promised insight without reading live amounts. Category/person names may remain intentionally live; label this behavior in the design contract.
- Create the report inputs, staleness record, and closing row from a consistent database snapshot. Only completed local calendar months may be closed.
- Recalculation replaces the stored values only after confirmation. The dialog identifies the month and explains that the previous snapshot will be replaced.

**Acceptance:** two previous months with identical net result but different spending generate different correct comparisons. Uncategorized winners, empty months, refunds, ties, renamed categories, and purged largest expenses render deliberately in both languages.

## Reliable staleness detection

Replace the aggregate/max-timestamp heuristic with a deterministic record of the relevant ordered inputs for the selected month and the previous comparison month. Canonical serialization with existing serde support can serve as the stored comparison record without a new hashing dependency. If a digest is later chosen, declare that dependency change explicitly.

Include fields that change captured financial values or the promised stale-state behavior, including transaction identity, date, type, amount, category assignment, title, and retained record timestamps. Include previous-month comparison inputs. Do not include intentionally live category/person names solely to mark a label rename as a financial change.

Compute/cache this work on data/date/selection invalidation, never on every rendered frame. Reopening the app must reproduce the same comparison result.

**Acceptance:** editing a non-maximum-timestamp row, imported future timestamps, clock rollback, moving a row between months, soft delete/restore, and editing the previous month all update the appropriate stale state. An unchanged database does not. Recomputing a stale closing clears the indicator.

## Import/export completeness and compatibility

- Write **document format `5`** in `1.4.0` (superseding the pre-D9 `format 3` assignment) for goals, contributions, and closings. Accept formats `1`–`4` through explicit per-version adapters; earlier readers reject higher formats before replacement. Keep database migration versions independent from export format versions.
- Extend the validation and transaction boundary with goal/contribution/closing references, IDs, timestamps, valid calendar months, checked aggregates, and snapshot numeric invariants.
- Preserve all representable IDs and recorded metadata. Do not claim metadata absent from a format-1 export is recovered exactly.
- Continue to export live transactions only. If the largest-expense reference is absent from the exported rows, export a null reference and retain its title/amount fallback. Explain that a full database backup is the restore path for trash.
- JSON round-trip tests compare the full canonical payload, including nonempty goals, contributions, closings, and prior-version defaults. A failed replacement test starts with existing data.
- XLSX adds localized Goals and Closings sheets with explicit full-history scope. Existing monthly sheets continue to obey their selected scope; each sheet labels its range.

**Acceptance:** format-1 through format-4 documents import deliberately; format-5 documents retain all collections; invalid months such as 2026-13, dangling references, overflowing sums, and inconsistent snapshots are rejected without modifying existing data.

## UX and visual acceptance

- Goals show name, attribution, funded amount/target, remaining or excess, status, deadline, and a clear primary action. Distinguish funding progress from lifecycle status following D4.
- Provide useful Active/Paused/Completed/Archived filtering without a wall of simultaneous actions. Detail lists remain readable with long notes and scaled text.
- Closing cards explicitly distinguish saved values from live month summaries. The calendar marker means a snapshot exists; its accessible description also conveys stale state where applicable.
- Preserve keyboard navigation and focus after contribution removal, archive, restore, and recalculation. Keep existing `Ctrl+1/2/3`, Trash on `Ctrl+4`, and add Goals on `Ctrl+5` with visible shortcut hints.
- Follow the approved Semibold/Bold hierarchy, tabular financial values, both themes, reduced motion, and responsive width rules. Never animate through fictitious intermediate money values.
- Goals and closing surfaces inherit the shared 1.1–1.3 wallpaper, appearance preferences, rendering lifecycle, and accessibility fallbacks. The user's cross-main-screen GIF scope includes Goals. Preserve clear saved/live distinctions over every wallpaper; do not duplicate the renderer or media cache in the Goals screen.
