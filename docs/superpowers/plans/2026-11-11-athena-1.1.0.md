# Athena 1.1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the six high-value habits to Athena: who-owes-whom, one-line entry, undo/trash, automatic backups, day drill-down, monthly insight, plus templates, duplicate warnings, and XLSX export. Payer data already exists from 1.0.

**Architecture:** Migration `0002` adds soft delete and templates. Existing services stay; new services add settlement, parsing, backup, insight, duplicate detection, and XLSX. UI gains a trash screen, template chips, day filter, and backup controls. All new copy goes through `i18n/mod.rs` in both languages.

**Tech Stack:** Same as 1.0.0, plus `strsim` 0.11 and `rust_xlsxwriter` 0.102.

**Spec:** `docs/superpowers/specs/2026-11-11-athena-design.md`

**Base:** Athena 1.0.0 shipped and tagged. `transactions.payer_id` exists.

## Architecture Amendments (review 2026-11-12)

**State mapping (review 2026-11-12):** the old single `AppState` is `AppCore { store, vm, ui }` (see 1.0 Task 9). In this release: writes -> `Store::apply(AppAction)` (existing `DeleteTransaction` becomes a soft delete; new actions: `RestoreTransaction`, `PurgeTransaction`, `SaveTemplate`, `DeleteTemplate`, `CreateBackup`, `RestoreBackup`, `ImportJson`); reads -> `ViewModel` (`templates`, `trash_count`, `settlement`, `insight`, `backups`); ephemeral UI -> `UiState` (`filter.day`, template chips, duplicate-warning state). Screens receive `&ViewModel, &mut UiState, &mut Vec<AppAction>`. A task line that still says `AppCore::x` means the matching `Store`/`ViewModel`/`UiState` item. <!-- lint:allow -->


These override any conflicting detail in the tasks below.

- **Task 1:** Migration `0002` also creates `CREATE VIEW live_transactions AS SELECT * FROM transactions WHERE deleted_at IS NULL;`.
- **Task 4:** Do not add `deleted_at IS NULL` by hand. Every list, report, settlement, search, insight, duplicate, and export query reads `live_transactions`. Only the trash repo, restore/purge, the transaction write path, and the import repo touch `transactions` directly. Add the integration test `tests/no_transactions_table.rs`: it scans `src/infrastructure/**/*.rs`; any `FROM transactions` / `JOIN transactions` fails unless the file is `trash_repo.rs` (trash only) or the statement is one of `INSERT INTO transactions`, `UPDATE transactions`, or `DELETE FROM transactions` in `transactions_repo.rs` / `import_repo.rs`. Reads in `transactions_repo.rs` must use `live_transactions`. Undo is implemented as the inverse `AppAction` returned by `Store::apply`. <!-- lint:allow -->
- **Task 5:** Rotating backups extend the 1.0 `daily_snapshot` (`VACUUM INTO` + integrity check) instead of adding a second mechanism. Manual backups keep 30; auto-snapshots keep 7.
- **New Task 5b: JSON import (restore from export).** Moved forward from 1.3. Import into an empty database or replace the current one after a pre-import snapshot. Validates `schema_version`, allocation sums, and references before writing; one SQL transaction. Round-trip test: export -> import -> export is byte-identical apart from `exported_at`. This relies on rules fixed in 1.0 Task 16: deterministic ordering, and ids and timestamps preserved exactly as exported (import inserts with explicit ids). Documents written by 1.0 omit `templates`; every collection added after 1.0 is `#[serde(default)]` so older documents import. Tests: `imports_a_1_0_document_without_templates`, `rejects_allocation_sum_mismatch`, `rejects_unknown_person_reference`, `import_is_all_or_nothing`.
- **Task 7, Task 10:** Insight sentences and XLSX headers use `crate::i18n` (top-level module), never the UI layer.

## Global Constraints

- All 1.0 constraints still apply.
- Bump `Cargo.toml` to `version = "1.1.0"`.
- Soft delete replaces hard delete for user-facing deletion.
- Backups never overwrite an existing file.
- Duplicate detection warns. It never blocks or auto-deletes.
- Templates prefill only. They never save automatically.
- One-line entry parses into the form. It does not save on first Enter.
- XLSX export is atomic like JSON/CSV.
- Every new visible string exists in English and pt-BR.

## Review Focus

1. **Soft delete leaks:** deleted rows must vanish from month, calendar, reports, settlement, search, and exports. Restore must bring them back complete with allocations.
2. **Backup restore:** restoring must not destroy the current DB before a snapshot exists. A failed restore must leave the app usable.
3. **Payer data from 1.0:** historical rows may have `payer_id = NULL`. Settlement must count and surface them, not silently treat them as owner-paid.
4. **One-line parser:** titles containing numbers must not steal the amount. `2 pao 10,00` parses amount `10,00`, title `2 pao`.
0. **Upgrade path:** a database created by 1.0 (user_version 1) with real rows upgrades to 2 with data intact; `live_transactions` shows all existing rows.
5. **Duplicate false positives:** same amount on the same day but different title must not warn. Warning must not fire on edit of the same row.
6. **Template prefill:** using a template must not persist a transaction until the user saves.
7. **Localization:** settlement sentence, insight, trash, templates, duplicate warning, and XLSX headers all switch language.

No `..Default::default()`: the fixture names every 1.1 field explicitly, which is what makes a forgotten new collection a compile error rather than silent data loss. Later releases add their fields with `#[serde(default)]` and extend this fixture.

## Self-Review Notes

- Every 1.1 feature has a task and a test.
- Payer is already in 1.0; this release only surfaces settlement and missing-payer counts.
- Soft delete touches every report, export, and settlement path; `live_transactions` is the single read path.
- JSON import is validated, atomic, and round-trips 1.0 documents without templates.
- Backups prune per prefix; restore never runs before a pre-restore snapshot exists.
- XLSX uses the shared `ExportScope` and the shared atomic writer.
- Templates and one-line entry never auto-save.
- Duplicate warning is non-blocking.
- All new strings ship in English and pt-BR.
