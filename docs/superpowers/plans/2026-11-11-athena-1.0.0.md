# Athena 1.0.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a polished local-first desktop app for fast household expense logging, a monthly register, and year-calendar browsing, backed by SQLite, exact decimal money, and English/pt-BR UI.

**Architecture:** Rust binary plus library. `domain` holds money, dates, settings, entities, validation. `infrastructure` owns SQLite, migrations, repositories, export. `application/services` orchestrates use cases. `app` holds state and navigation. `ui` renders egui screens and calls state methods. UI never issues SQL. All visible copy flows through `i18n/mod.rs`.

**Tech Stack:** Rust 2024, eframe/egui 0.37, rusqlite 0.42 (bundled), rust_decimal, chrono, serde, csv, rfd, sys-locale, tracing, winresource, fs4, unicode-normalization.

**Spec:** `docs/superpowers/specs/2026-11-11-athena-design.md`

## Architecture Amendments (review 2026-11-12)

These override any conflicting detail in the tasks below. The design spec §7 and §10 are the source of truth.

- **Task 1:** Data dir resolves to `<exe dir>\data\` when `athena.portable` sits next to the exe, else `%APPDATA%\Athena\`. Add a single-instance guard: exclusive `fs4` lock on `<data dir>\athena.lock`, released by the OS when the process exits; a second launch shows "Athena is already running" (message box) and exits non-zero. Add `proptest` and `egui_kittest` as dev-dependencies.
- **Task 2:** `proptest` for money parse ↔ format round-trip and for the >2-decimals rejection rule.
- **Task 3:** `TxDraft`/`Transaction` gain `split_mode: Option<SplitMode>` (`Even | Custom`, `None` when unassigned or single person); `payment_method` is removed. `proptest`: split shares always sum to total and never differ by more than 1 cent under even weights. <!-- lint:allow -->
- **Task 4:** Schema per spec §9: `categories.applies_to IN ('expense','income','both')` (seeded: Salary/Other income = `income`, rest `expense`), `transactions.split_mode`, no `payment_method`. Timestamps are UTC RFC 3339 (`2026-11-12T14:03:00Z`). Pre-migration backup uses `VACUUM INTO ?1` (bound path) followed by `PRAGMA integrity_check` on the copy, never a raw file copy. Add `backup::daily_snapshot(conn, &AppDirs, today)`: on startup, if no `auto-YYYY-MM-DD.db` exists for today, `VACUUM INTO` it and keep the newest 7. <!-- lint:allow -->
- **Task 6:** `TransactionsRepo::save_with_allocations` is the only write path for transactions and allocations. Add `integrity::check(&Connection) -> Vec<IntegrityIssue>` (allocation sum ≠ amount, allocation on a missing person). Called in tests and at startup under `debug_assertions`.
- **Task 7:** Layering rule: SQL aggregates live in `infrastructure/db/reports_repo.rs`; `domain/reports.rs` holds pure result types and arithmetic; `application/services/reports.rs` only composes. No SQL outside `infrastructure`.
- **Task 8:** i18n lives in `src/i18n/mod.rs` (top-level, not under `ui`), so application services and exporters can use it without depending on the UI layer. Strings are a `Strings` struct with one `&'static str` field per key; each language is one `const Strings`, so a missing translation is a compile error.
- **Task 9:** Split the old single state into `app/store.rs` (`Store`: owns `Db`, exposes use cases, bumps `data_version: u64` on every committed write), `app/view_model.rs` (`ViewModel`: cached month/year/people/categories, reloads only when `data_version` changed) and `app/ui_state.rs` (`UiState`: screen, month, calendar year, filter, dialogs). `AppCore { store: Store, vm: ViewModel, ui: UiState }` lives in `src/app/mod.rs`. Writes go through `Store::apply(AppAction)`, reads come from `ViewModel`, ephemeral state lives in `UiState`. `AppCore` methods (`create_transaction`, `set_month`, ...) are one-line wrappers: build the `AppAction`, call `store.apply`, then `vm.refresh(&store)`. They hold no logic. Screens never receive `AppCore`; they get `&ViewModel`, `&mut UiState`, `&mut Vec<AppAction>`. `ViewModel` holds **all** people and categories (archived included) for label lookup, plus `active_people()` / `active_categories(kind)` for pickers. Where later tasks say `AppCore::x`, write methods map to `Store`, read methods to `ViewModel`, and ephemeral setters to `UiState`.
- **Task 11:** `AppAction` is the only mutation path from the UI, including `CompleteOnboarding` and the Task 16 export actions. `Store::apply(AppAction) -> Result<ActionOutcome>`; the app loop shows the toast and triggers view-model refresh. Quick add filters categories by `applies_to` matching the selected kind. Payment method field removed.
- **Task 16:** CSV export takes an optional `YearMonth` filter; default file names `athena-YYYY-MM.csv` / `athena-all.csv` (CSV) and `athena-full-YYYY-MM-DD.json` (JSON).
- **Task 17:** Add `egui_kittest` snapshot tests for: empty first launch, month with data, both languages, both themes. Smoke checklist keeps only what snapshots cannot cover. README documents `athena.portable` and the daily auto-snapshot.

## Global Constraints

- Rust edition `2024`, `rust-version = "1.95"` (required by eframe/egui 0.37).
- `[lints.rust] unsafe_code = "warn"`. `[lints.clippy] all = "warn"`, `pedantic = "warn"`.
- Money source of truth: `i64` cents inside `Money`. Never `f32`/`f64` for money.
- Currency: BRL only. Display `R$ 1.234,56`. Input accepts `45`, `45.90`, `45,90`, `1.234,56`, `R$ 1.234,56`, and leading `-`. Reject more than two decimal places. Never round silently.
- Dates: `chrono::NaiveDate`, stored ISO `YYYY-MM-DD`. Month is local calendar month, Monday-first.
- Database file: `%APPDATA%\Athena\athena.db`. Logs: `%APPDATA%\Athena\logs`.
- Runtime is fully offline.
- No transaction title or description in log output.
- Every multi-row write runs in one SQLite transaction.
- No `unwrap()` / `expect()` in production paths. Tests may use them.
- UI copy is English and pt-BR, selected by `profile.language`. No visible string literals in screens.
- Owner name lives only in `people`. `profile` has no display name.
- Payer is recorded in 1.0.
- Delete in 1.0 is hard delete with confirmation. Trash arrives in 1.1.
- Transfers and multiple accounts are out of scope.

## Review Focus

1. **Money input:** pt-BR and plain formats, thousands separators, `R$` prefix, empty, letters, negative, more than two decimals. Parse or reject with a clear message. Never truncate or round silently.
2. **Odd-cent and invalid split:** `R$ 0,01` across three people sums exactly. Zero-cent allocations are valid. Empty weights and all-zero weights return an error.
3. **Month boundary:** a transaction on the last day and first day of adjacent months appears in the correct month in register, calendar, and reports.
4. **Empty state:** first launch, no profile, no transactions, no partner. No panic, no blank card, no `NaN`, no division by zero.
5. **History after rename/archive:** renaming a category or person updates historical labels. Archiving hides it from pickers, keeps old transactions readable, and keeps totals stable.
6. **Payer integrity:** payer is stored from the first release. A null payer is valid but visible. Payer must reference an existing person.
7. **Owner identity:** sidebar, settings, and transaction attribution all read the owner `people` row. No second name source.
8. **Localization:** switching language updates every screen, month and weekday names, and export headers without restart.
9. **Migration safety:** newer schema refuses to open. Failed migration rolls back. Pre-migration backup exists.
10. **Export safety:** CSV and JSON are atomic. A failed export leaves the previous file intact.

- [ ] **Step 3: Implement `Money`**

Parse steps: trim; remove ASCII and NBSP whitespace; remove every `R$` so `-R$ 10,00` and `R$ -10,00` are equivalent; accept at most one leading `-` or `+`; reject any remaining character outside digits, `.` and `,`.

Then normalize unambiguously:
- If `,` is present, it is the decimal separator. There may be at most one `,`; every `.` must appear before it and is removed as a thousands separator. Reject a `.` after the `,` (`1,234.56`).
- If no `,`, more than one `.` means thousands separators when every group after the first has exactly 3 digits; remove them.
- Exactly one `.` with exactly 3 trailing digits and a non-zero digit before the dot is thousands (`1.234` → 1234). Otherwise the dot is decimal, so `0.005` and `45.90` both go through the precision check.

Count digits after the final decimal separator; more than two returns `TooPrecise`. Parse with `rust_decimal::Decimal::from_str`, multiply by 100, convert to `i64`, return `TooLarge` on overflow. No rounding.

Format: use `unsigned_abs` to avoid `i64::MIN` overflow; group integer part with `.`, decimals with `,`, prefix `R$ `, negative prefix `-`.

`br_number`: `1234,56`. No prefix, no thousands separator.

### Task 16: JSON and CSV export

**Added (review 2026-11-12):** `ProfileDocument` is only compilable because Task 2/3 added `Serialize, Deserialize`. New vectors added in later releases must use `#[serde(default)]` so older documents still parse. Export ordering is deterministic (people by id, categories by id, transactions by `date, id`, allocations by `person_id`) and ids and timestamps are written as stored, which is what makes the 1.1 import round-trip byte-comparable. CSV values starting with `=`, `+`, `-`, `@` are prefixed with `'`. Export scope: `ExportScope { All, Month(YearMonth) }` is an explicit argument; exporters never call `Local::now()`. <!-- lint:allow -->

- CSV text cells beginning with `=`, `+`, `-`, or `@` get a leading `'` after normal CSV quoting. Numbers and dates are written unchanged.
- Export queries use `ORDER BY t.date ASC, t.id ASC`. Both formats share one order so tests can select rows by title.
- Both use temp file + validate + persist through `atomic_write`.
- Adds `AppAction::ExportJson`, `AppAction::ExportCsv`, applied in the app loop.
