## Overall view

The Tasks 1–6 code is careful work. Migrations, the query boundary, settlement arithmetic and the effects matrix match the contracts closely, and the tests cover them well. The problems sit at the seams between features. Retention depends on a snapshot nobody validates. The repair filter depends on filter state nobody clears. The whole read model depends on one optional calculation that can fail. Tasks 7–10 (backup files, restore, format 2, import) are missing. Because the snapshot fallback promised in §6.2 can't yet be used from inside the app, retention is already deleting data permanently without the recovery path the design assumes.

Release readiness: **not ready. That is expected mid-plan.** Do not cut any build from `5ba7411` for real data, even an internal one. It purges trash, and its JSON export writes format-1 documents containing settlements, which §10.3 forbids (see O-6).

Classification key: **R** = reproduced by a test I ran; **I** = found by reading the code; **S** = a gap or contradiction in the specification; **F** = a future task not yet implemented (not a defect).

## New findings (prioritized)

### O-1 — P1, R: retention also trusts a valid but foreign snapshot file
- Evidence: `backup.rs:85-87`, `store.rs:53-60`. Probe `valid_but_foreign_sqlite_file_as_snapshot_still_allows_purge`: a SQLite file holding only `CREATE TABLE unrelated(x)` at today's `auto-` path. `integrity_ok` returns `true`, startup runs, and the trash count goes from 1 to 0.
- Why it matters: this is the same destructive consequence as Codex 1, and it defeats the obvious fix.
- Required behavior (proposed): before purging, the snapshot must be an Athena database (`application_id == 0x41544E41`) at `user_version == latest_version()`, pass `integrity_ok`, and contain every row id in the purge set with `deleted_at IS NOT NULL`. The cheapest robust alternative: when the purge set is non-empty and the existing snapshot fails validation, write a fresh verified snapshot under a distinct name (for example `pre-purge-…`; this needs a §9.1 amendment). If that fails, skip the purge. Tests: corrupt, empty, directory, foreign schema, older schema, a snapshot missing the rows.

### O-2 — P2, R: one settlement overflow breaks the whole view model and can stop startup
- Evidence: `view_model.rs:210` (`self.settlement = Some(settlement::for_month(..)?)`) inside the all-or-nothing reload. `app/mod.rs:65` runs `core.sync()?` in `AppCore::new`. Probe `settlement_overflow_fails_whole_view_model_sync`: two valid settlements of 5×10¹⁸ cents from the same person make `for_month` return `Err` and `vm.sync` return `Err`. The probe's final assertion "failed" because `vm.transactions` had *already been replaced* before the error. So the view model is left **partially updated** (new register, stale summaries and settlement), and `loaded` is not advanced. As a result:
  - at startup, `AppCore::new` fails and the app does not open;
  - while running, `show()` logs and calls `sync` again **every frame**, a full database reload per frame;
  - in `AppCore::apply` (`app/mod.rs:100-104`), a committed action whose reload fails returns `Err`, so the UI reports a failed save that actually committed, and its undo inverse is lost.
- The cause is new in 1.1. Settlements are excluded from the SQL `SUM`s, so the reports cannot overflow on them, but the settlement calculation can. §10.4's aggregate checks (income, expenses, refunds, start + net) also skip per-person settlement totals, so a future import could bring this state in.
- Proposed fix: on `Err`, show settlement as unavailable (`settlement = None`, log once) instead of failing the reload. Stage the reload into locals and commit them together. Extend §10.4 to check the per-person paid/owed totals with checked arithmetic.

### O-3 — P2, I/S: retention runs before any in-app restore exists
- §6.2 justifies early purges with "the same launch's snapshot holds those rows". At `5ba7411` there is no restore (Task 8) and no recovery (Task 11). Getting a row back means hand-copying files. Snapshots are pruned to the 7 newest (`backup.rs:12, 89`), so a purged row stays recoverable for about a week. The Trash copy (`i18n/en.rs:101`) doesn't say how long.
- Release gate: retention must not ship without Task 8. Hydrogen should decide whether to disable retention until Task 8 lands, and whether the Trash hint should name the 7-day window.

### O-4 — P3, S: Record on a past or future month's card uses that month's balance but today's date
- `app/mod.rs:290-303` with §7.4 (`date = vm.today`). The card shows balances "as of" the last day of the selected month (T1), and every transfer row offers **Record** (`settlement_card.rs:117-127`). Recording October's suggestion on 16 Nov ignores everything between 1 Nov and today, so the household can over-settle or under-settle. A future month's card would count future-dated rows.
- Proposed: offer Record only when `as_of >= vm.today` and the month is the current one, or compute it as of `min(as_of, today)`. This needs a §7.4 decision.

### O-5 — P3, I: stale Undo toast after a permanent delete fails silently
- `app/mod.rs:526-533`: a purge or empty-trash outcome has no toast, so an earlier "Deleted · Undo" toast survives. The toast pauses while hovered (§6.3). Sequence: delete X, press Ctrl+4, choose Delete forever on X, then press Undo or Ctrl+Z. `RestoreTransaction` returns `NotFound`, and `apply_undo` (`app/mod.rs:412-415`) only logs a warning. The user sees nothing.
- Proposed: clear a toast whose undo targets a purged id, or clear on any `RefreshScope::Trash` outcome, and give feedback when undo fails.

### O-6 — P3, I/F: interim JSON export writes format 1 with settlements
- `infrastructure/export/json.rs:22-36`: `SCHEMA_VERSION = 1`, with serde derived from domain types, so `kind: "settlement"` is written into a format-1 document. §10.3 says "Format 1 cannot contain settlements", so the 1.1 importer will reject these files. Task 9 fixes the writer. The risk is any interim build used on real data, and that hazard sits alongside the retention one. The comment at `json.rs:33` ("Templates arrive in 1.1") is also stale under D9.

### O-7 — P3, I/S: the CSV cannot show who paid a settlement
- `infrastructure/export/csv.rs:41-72` has no payer column. A settlement row lists only the recipient under People, so the direction survives only in the free-text title. §5.3 requires a row and the kind but says nothing about direction. Also, §5.3's "kind column `settlement`" conflicts with the existing localized labels ("Settlement"/"Acerto", which `export.rs` tests assert). The contract should say which one is meant.

### O-8 — P3, I: every screen switch and search reloads everything, including the full-history settlement
- `view_model.rs:145-178`: `LoadKey` contains `screen` and `filter`, and `sync` always reloads `RefreshScope::All`. Each navigation and each debounced search reruns `settlement_repo::list_inputs` over **all** live rows and allocations (`settlement_repo.rs:16-50`), plus the calendar and the lifetime balance. This is correct, but at the 50,000-row reference size it will cost noticeable time. It belongs to 1.2 "Daily speed", but this is the moment to note it: per-field keys (settlement depends only on `version` and `month`) would avoid it.

### O-9 — P3, I: `RestorePerson` failure shows generic copy
- `app/mod.rs:305-322` maps every error, including the expected name-uniqueness conflict (`people_repo.rs:105-108`), to `settings_save_failed`. §12 requires localized error copy. This one needs a specific message ("another active person is already named Ana").

## Areas checked with no defect found

- **Migrations (§4):** `0002` and `0003` match the contract text exactly. The foreign-keys-off runner restores the prior value on success and on error (`migrations.rs:77-84`). `foreign_key_check` rolls back. The id high-water test is meaningful: without the sequence carry-over the next id would be 3, and the test asserts ≥ 4. The v1 table constraints are a subset of v3's, so the copy cannot fail on existing 1.0 rows. Pre-migration backup is in place. Caveat: a backups folder that can't be written still blocks startup, with no recovery until Task 11 (pre-existing).
- **Query boundary (§6.4):** every non-test direct `transactions` reference lives in an allow-listed file. CSV and JSON export use `transactions_repo::list`, so live rows only. The behavioral matrix `deleted_rows_vanish_everywhere` covers settlement, CSV and JSON.
- **Effects matrix (§5.3):** `SUMMARY_SELECT`, the year summaries, and the person, category and day totals all exclude settlement, including `count`. Shared-only excludes settlement. The person filter matches the settlement payer or recipient.
- **Settlement arithmetic (§7):** checked throughout, exclusion order as specified, archived parties included, greedy matching with lower-id tie-breaks, and a proptest that balances sum to zero.
- **Undo and keyboard:** the explicit shortcut table matches §8.4. Ctrl+Z is suppressed while a text field has focus. Undo of an update is unchanged from 1.0.
